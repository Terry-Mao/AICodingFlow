# 夜间存量代码审查

`review-existing-code.yml` 为已进入默认分支的代码提供周期性审查，帮助发现未在 PR 审查时暴露的旧 Bug。它与 PR review 分开运行，不把存量缺陷归因于当前 PR。

## 触发和覆盖

- 每天北京时间 02:30 触发一次。GitHub Actions 使用 UTC cron `30 18 * * *`，对应次日北京时间 02:30。
- 代码路径通过稳定哈希分配到周期分片，默认 7 天覆盖全部合格的 UTF-8 文本代码文件。Actions variable `NIGHTLY_REVIEW_CYCLE_DAYS` 可将周期设为 1–90 天；`workflow_dispatch` 可临时覆盖周期和指定分片补跑。空分片会复查一个文件，避免当天完全跳过。变更周期会重新分配文件，新的完整覆盖期从变更后开始计算。符号链接和二进制文件不作为审查目标。
- 审查默认分支的固定提交。每次先理解完整项目的入口、配置和跨文件调用链，再深入审查当天重点。源码、工作流、脚本和操作性 SKILL 是代码清单；测试、文档、spec、依赖和生成目录可作为核实上下文。跨文件追踪发现的根因可定位到重点范围外的项目代码文件。

## 发现与发布

工作流生成 `context.json`、`issues.json` 两份固定输入。`context.json` 同时记录完整项目代码清单和当天重点文件。Agent 只能检查代码并写 `findings.json`，每项包含文件与行号、触发条件、影响、证据、高置信标记和重复 Issue 编号。空结果必须写为 `{"findings": []}`。

外层脚本验证 JSON 结构、目标行、源文件摘要和写入范围，再与已有 open/closed Issue 查重。通过校验且未重复的发现逐项创建中文 Issue。普通 Issue 包含稳定指纹、扫描提交和定位证据；重跑同一分片不会重复创建相同 Issue。安全问题允许公开建单，但公开 Issue 只包含位置和影响，不发布具体触发步骤或核实细节；Agent 也不得在运行产物中写入敏感信息、利用载荷或逐步滥用说明。

无可审查文件或无合格发现时不建单。模型、校验或 GitHub API 失败时工作流失败，并上传可用运行产物供排查。新建 Issue 会进入现有 triage 流程，但不会自动获得实现许可标签。
